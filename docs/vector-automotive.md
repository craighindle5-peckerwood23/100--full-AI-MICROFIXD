# Vector Automotive MVP

Implemented inside the canonical TypeScript/Express application. The proposed Python tree is a domain map, not a second server or database. No empty placeholder files, second Postgres, Redis, or Ollama runtime are introduced.

| Proposed responsibility | Canonical implementation |
| --- | --- |
| Vehicle, case, hypothesis, test, observation, repair and verification models | `server/automotive/schemas.ts` |
| Database session and repositories | `server/automotive/database/` |
| DriveIQ retrieval and vehicle applicability | `server/automotive/driveiq/` |
| TorqueLogic hypotheses, test selection and state machine | `server/automotive/torquelogic/` |
| Redline safety screening | `server/automotive/redline/safetyEngine.ts` |
| BlackBox case event ledger | `server/automotive/blackbox/eventStore.ts` |
| Diagnostic workflow | `server/automotive/workflows/diagnosticWorkflow.ts` |
| VIN decoding | `server/automotive/integrations/vinDecoder.ts` |
| Vehicle and diagnostic API | `server/automotive/automotiveRouter.ts` |
| Runtime entrypoint | Existing `server/index.ts` |
| Technician workspace | `src/automotive/AutomotiveWorkspace.tsx`, path `/automotive` |

## Run and integrate

Apply `supabase/automotive_schema.sql` once to the same Supabase project used by the server. Requires pgvector in the `extensions` schema. Use existing `SUPABASE_URL` and server-only `SUPABASE_SERVICE_ROLE_KEY` / `SUPABASE_SECRET_KEY`. There is no local storage fallback for cases.

Open **Vector Automotive** in the OS, or `/automotive`. Existing Supabase account mode and RBAC apply. Shared operator credentials are restricted to the existing `default` tenant; authenticated accounts use their verified profile tenant. Browser-supplied tenant IDs are not accepted. Observers can read but cannot write; knowledge import requires administrator role. Tables and ranking function are server-only with RLS and public grants revoked, matching existing server-side storage conventions. Service role bypasses RLS; tenant enforcement therefore lives in the repository and verified server context.

Create a vehicle with exact engine identifier, import authorized knowledge, start a case with complaint and DTCs, record measured test findings, record work actually performed, then verify it. Case writes and event updates are atomic in a versioned row. A stale revision returns HTTP 409; refresh the case before retrying. Last 100 vehicles/cases are shown; per-fitment retrieval is bounded at 499 knowledge records and fails explicitly at 500. Each case is capped at 1,000 ledger events. These limits should become pagination before scaling.

Microfixd's governed planner discovers `list_automotive_cases` and `read_automotive_case`. Both read the mission tenant via the same repository, with automatically recorded read-only approval receipts. Select them in the existing mission tool controls. Models cannot record observations, claim a repair, or enter verification through these tools; technician writes use the authenticated workspace/API.

## API

All paths are under `/api/automotive`:

- `GET/POST /vehicles`
- `GET /vin/:vin` (NHTSA vPIC, fixed host, timeout, rejects partial/error decodes; exact engine still requires confirmation)
- `GET/POST /cases`, `GET /cases/:id`
- `POST /cases/:id/evidence` (refresh only cases with no prior evidence)
- `POST /cases/:id/actions` (strict observe/repair/verify actions with expected revision)
- `GET /cases/:id/report` (full JSON provenance and ledger)
- `POST /knowledge` (admin-only, strict structured records)

## DriveIQ knowledge contract

No licensed OEM corpus is bundled. Source URL and excerpt are administrator-supplied provenance, not proof that this software fetched or independently validated the source. Import only material you have rights to use and check vehicle fitment and procedures before use. The application never manufactures a generic repair for missing evidence.

Knowledge JSON fields: `source` (HTTPS), `title`, `excerpt`, `make`, `model`, `engine`, `yearFrom`, `yearTo`, `dtcs` (array), `symptoms` (array), `cause`, `repair`, and `test` with `id`, `title`, `procedure`, `expected`, `verification`, `risk` (`routine` or `specialist`), and `minutes`. IDs are generated by the server. Inspection and diagnostic specifications must come from the authorized source, not invented example values.

Exact DTC/symptom matching and strict year/make/model/engine applicability work without model credentials. Optional `AUTOMOTIVE_VECTOR_SEARCH=true` enables `text-embedding-3-small` (1536 dimensions) with `OPENAI_API_KEY`. This sends complaint/DTC text and imported knowledge text to OpenAI, consumes API quota, and ranks applicable knowledge with pgvector cosine distance. Enable deliberately. Provider failure returns an error rather than fake embeddings. Already-imported records without embeddings remain available through exact matching; re-import them after enabling vector search to embed them. Cosine order is a relevance ranking, not diagnostic confidence. Exact DTC or symptom evidence is still required to generate a hypothesis. No semantic-only diagnosis is claimed.

## Verification and limits

Evidence status is untested/supported/refuted/inconclusive, never an invented probability. Contradictory observations stay inconclusive and require review outside this MVP. Repair candidates require supporting test observations. Verification requires technician confirmation, measured findings, resolved complaint, absent relevant DTCs after an appropriate operating cycle, and a passed source-prescribed test. Failed verification returns the case to testing. Successful verification closes the case against further mutation. These are technician attestations, not hardware-certified test results.

Safety flags or detected safety-critical complaints hold the case; this MVP does not implement clearing those holds. Specialist tests require an explicit qualified-technician confirmation. Screening is conservative and not exhaustive.

OBD connections/streaming, ECU/TCM/BCM writes and flashing, OEM bulk ingestion, recall synchronization, forecasting, automatic learning, automated numeric observation interpretation, and self-healing are future extensions. Their directories are not presented as working features. The current implementation is a bounded evidence-driven diagnostic workflow.

Run `node --import tsx --test tests/automotive.test.ts`, then `bash scripts/verify-production.sh`. Production capability requires deploying the reviewed commit and verifying authenticated API behavior; a passing build alone is not live proof.

## Validation for this implementation

- Production gate: 99 tests passed, TypeScript passed, classification validated 60 typed objects and 46 organ routes, deterministic release evaluation approved, both frontend builds passed.
- Browser: `node --import tsx tests/automotive-ui.mjs` completed the create/observe/repair/verify flow using synthetic fixtures through the actual router, and checked desktop/mobile layouts. This is not live OEM or OBD validation.
- Supabase: additive schema installed on the existing Microfixd project; `supabase/tests/automotive.sql` passed against that project. Fixtures were rolled back. Checks cover revoked public grants, RLS, tenant/engine/year filtering in vector ranking, and compare-and-set update fencing.
- OpenAI embedding generation and live NHTSA decoding were not exercised with production credentials/vehicles. Deployment and authenticated production API verification remain separate release steps.
